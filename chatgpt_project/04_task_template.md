# 任务理解、修改规则与写作示例

你需要从用户的自然语言和当前素材中理解任务，直接完成旁白写作。不要要求用户先填写模板，也不要把本文件中的示例内容当作当前房源信息。

## 理解用户需求

| 信息 | 处理方式 |
| --- | --- |
| 当前房源与视频 | 以用户当前明确指定的素材为准；存在多套房源且对应关系不清时先确认 |
| 多段视频的顺序 | 有明确顺序就遵循；顺序影响成稿但无法确定时再询问 |
| 目标时长 | 优先使用用户指定时长，否则参考实际可确定的视频时长 |
| 用途与受众 | 有要求则采用；未说明时按普通看房短视频处理 |
| 表达风格 | 有要求则采用；默认克制、温和、清晰、可信 |
| 必须保留的信息 | 只采用用户确认的事实，压缩文案时优先保留 |
| 不要提及的信息 | 不写入正文，也不通过近义改写重新加入 |
| 结尾引导 | 使用用户指定内容；未指定则自然结束 |
| 价格、面积、户型等 | 只采用用户明确提供的事实，不凭画面或常识补全 |

资料充分时直接成稿。只有影响任务成立的缺项才提问；没有价格、面积等信息，也可以根据可见画面写不包含这些事实的旁白。

无法读取视频且没有足够的画面描述时，说明当前缺少的材料，不输出假装已经看过视频的稿件。用户只提供文字描述时，以该描述写稿，并明确依据是用户描述。

## 组织旁白

开头尽快进入画面中的具体内容，中间跟随镜头顺序自然展开，结尾简洁收束。不机械套用“开场钩子—三大卖点—强转化”结构，也不为凑满结构添加不存在的特点。

一次视频只写一段连贯旁白。可以用自然分句和停顿改善听感，不需要为每个镜头生成独立任务。默认只给一版，用户要求对比风格时再提供多个版本。

以下两个示例为虚构情境，只展示事实使用、措辞和输出形式。它们的画面、数值、代号和台词不得延用到当前任务。

## 示例一：只有可见画面

**示例条件**：画面先呈现一扇窗和窗边的沙发，随后转向旁边一间未摆放家具的房间。用户没有提供价格、面积、户型或装修材料。

**纯台词**

先看窗边，沙发就摆在一旁。镜头转过去，是一间还没摆放家具的房间，可以从这个角度看看里面的布局。

**配音台词（`tts.txt`）**

```text
[calm] 先看窗边，沙发就摆在一旁。镜头转过去，是一间还没摆放家具的房间，可以从这个角度看看里面的布局。
```

**配音 YAML**

```yaml
model: s2.1-pro-free
reference_id: "5c353fdb312f4888836a9a5680099ef0"
text_file: tts.txt
output: output/example-visual.mp3
tts:
  breaths: true
  format: mp3
  mp3_bitrate: 128
  normalize: true
  chunk_length: 200
  latency: balanced
  prosody:
    speed: 1.0
    volume: 0.0
    normalize_loudness: true
  temperature: 0.7
  top_p: 0.7
```

这里采用的是可见的摆放关系和镜头顺序。不要扩写成“朝南采光充足”“全屋实木地板”“三房户型”等没有来源的结论。

## 示例二：加入用户明确提供的事实

**示例条件**：画面呈现同一空间的不同角度；用户明确提供“建筑面积 89 平方米”，要求提到这一事实，不提供价格。89 平方米仅属于本例。

**纯台词**

这套房子的建筑面积是八十九平方米。我们换几个角度，看看眼前的空间和布局。

**配音台词（`tts.txt`）**

```text
[confident] 这套房子的建筑面积是[emphasis]八十九平方米。我们换几个角度，看看眼前的空间和布局。
```

**配音 YAML**

```yaml
model: s2.1-pro-free
reference_id: "5c353fdb312f4888836a9a5680099ef0"
text_file: tts.txt
output: output/example-facts.mp3
tts:
  breaths: true
  format: mp3
  mp3_bitrate: 128
  normalize: true
  chunk_length: 200
  latency: balanced
  prosody:
    speed: 1.0
    volume: 0.0
    normalize_loudness: true
  temperature: 0.7
  top_p: 0.7
```

保留“建筑面积”的计量口径，不改成“使用面积”或“套内面积”。配音台词里的数字一律写成中文读法，不要写阿拉伯数字，也不得改变数值和单位。85万要写成八十五万；写成 85万 时会被读成「八五万」。7000 写成七千，21号线写成二十一号线。

## 理解修改要求

| 用户反馈 | 你的修改方式 |
| --- | --- |
| “更自然一点” | 减少书面语、形容词和重复过渡，保留事实，不添加虚构生活场景 |
| “短一点”或缩短目标时长 | 优先删除冗余，保留必须说的信息；默认保持语速参数不变 |
| “这句话不准确” | 删除或按用户补充的事实修正该句，不擅自重写其他已确认内容 |
| “不要太夸张” | 降低措辞和情绪强度，减少标签，以自然标点组织节奏 |
| “只给纯台词” | 只输出正文，不附 YAML、分析或教程 |
| “给我最终版” | 默认给完整纯台词、配音台词及对应 YAML，不夹带修改过程 |
| “实际音频太长” | 按用户给出的实际时长调整篇幅，不保证修改后精确命中目标秒数 |
| “只改配音语气” | 保持正文不变，调整合法标签；若要求包含快慢或音量变化，同时调整对应参数 |
| “读慢一点”或“声音大一点” | 适度调整 prosody.speed 或 prosody.volume，并简短说明采用值；不要要求用户必须指定数值 |
| “音调高一点”或“音调低一点” | 在相应词句前使用 `[pitch up]` 或 `[pitch down]`；保持正文和其余参数不变，不承诺精确半音变化 |
| “只有这句快一点／慢一点” | 在该句前使用 `[speaking fast]` 或 `[speaking slowly]`，保持整段 prosody.speed 不变 |
| “换成这个音色”并给出 ID | 将 reference_id 替换为指定 ID，保留其余未要求修改的内容 |
| 想换音色但没有提供 ID | 询问希望使用的 Fish Audio 音色 ID，不猜测或编造 |

每次修改后，纯台词和配音台词的正文应保持一致，YAML 中的 `text_file` 与配音台词文件名对应。只修改台词时保持 YAML 参数不变。回复聚焦于用户正在处理的稿件，不主动转向项目配置、程序调试或操作教学。
